# Push a small map, pull the rest

The best-proven shape for ORFE is a small index the model always sees, plain Markdown notes it pulls with tools, and hard rules in code that keep the vault clean. Compaction should run only at ORFE's existing trim, use a small model on fixed chunks, and leave every old message searchable on the phone. Retrieved text belongs in tool results, where it stays and never breaks the cache. Old tool results should become pointers by plain rule. A small model is right for summaries, but Jev should not decide what is kept. Poems, recipes and voice samples need a lock in the tool code, because prompts are only advice. Abilities should be a static list of plain tool data behind one host function. The evidence is strong on mechanics and weak on real outcomes, and nothing tests several models sharing one store, voice after compaction, or a personal vault of a few hundred notes. One finding conflicts directly with "memory is pulled, not pushed": pure pull fails when the model does not know what exists. I recommend you change the rule to "bodies are pulled, and only the map is pushed".

## The rule holds for note bodies, but the map must be pushed

**Pure pull lost the best test we have.** In Vercel's evals, the baseline passed 53%. A skill the model could load also passed 53%, because the model never invoked it in 56% of cases. Explicit instructions raised that to 79%. An always-visible 8KB index passed 100% ([Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)). This is one vendor and coding only. No study tests push against pull on personal memory.

**The rule still has good support for bodies.** An ETH study found that context files gave no general gain and raised cost by over 20% ([Gloaguen et al.](https://arxiv.org/abs/2602.11988)). The two results fit together. Vercel's index held what the model could not find alone. ETH's files repeated what the model could explore. Vault notes are the first kind, so the index should map and not summarise. Pull is also safer. A poisoned note that sits in the system prompt runs in every later chat, as SpAIware showed in ChatGPT ([Rehberger](https://embracethered.com/blog/posts/2024/chatgpt-macos-app-persistent-data-exfiltration/)). And pull is the only method that needs no cache work.

The rule is not in the design doc yet. I found it only in the research notes, so this is a good time to word it. These findings press on it.

| Finding | What gets pushed | Evidence | My suggestion |
|---|---|---|---|
| Models do not look up what they cannot see ([Vercel](https://vercel.com/blog/agents-md-outperforms-skills-in-our-agent-evals)) | The index | Medium. Vendor, coding only | **Direct conflict.** Accept it. Push titles and one-line descriptions. Push no bodies |
| Persona fidelity fell 41.27% over 100+ rounds, inside the context window ([Persistent Personas?](https://arxiv.org/html/2512.12775v2)) | Voice samples near the newest turn | Medium for the fade. Weak for the fix, which is community lore | **Direct conflict, undecided.** Keep samples pulled. Test a short reminder near the tail in a blind A/B |
| Full context beat BM25 by 10.2 points on temporal and multi-session questions ([preprint, not peer reviewed](https://prereview.org/preprints/doi-10.20944-preprints202608.1369.v1)) | The compaction summary | Weak to medium | **Partial conflict.** Accept it. A summary replaces text that was already sent, so it is context, not recall |
| About 66 of 452 models list no tool support. The feed's counts do not fully agree, so read the per-model field ([models feed, probed](https://openrouter.ai/api/v1/models?supported_parameters=tools)) | Nothing can be pulled on these models | Strong | **Hard limit.** Turn abilities off on these models and say so. Do not add app-driven recall by default |
| Weak models needed tool rules that forced them to search ([Letta](https://www.letta.com/blog/benchmarking-ai-agent-memory)) | An instruction, not content | Medium | **No real conflict.** Tell models to search before they say they do not remember |
| ChatGPT and OpenAI's cookbook inject memory at the start ([Tech Times](https://www.techtimes.com/articles/317840/20260605/chatgpt-memory-dreaming-update-openai-rewrites-personalization-engine-limits-audit-trail.htm), [OpenAI cookbook](https://developers.openai.com/cookbook/examples/agents_sdk/context_personalization)) | Whole memories | Weak. OpenAI's figures are internal and reported second-hand | **Opposing design.** Do not follow it. It is the automation you chose to leave |

**The index must be smaller than the notes assume.** ORFE's default window is 32,000 tokens (`src/lib/context.ts`). By my arithmetic, 300 notes at 15 tokens a line would cost 4,500 tokens, or 14% of the window. So the index should be a tree. It should show folders with counts, and expand only near what matters, as Letta shows a tree with descriptions ([Letta](https://www.letta.com/blog/context-repositories)). A cap near 2,000 tokens matches Vercel's 8KB, which lost nothing against 40KB. The cap is my suggestion and is not tested on notes.

**The index also breaks a rule in your code.** The comment in `src/lib/system.ts` says "nothing dynamic goes in". Hermes solves the same problem with a snapshot that is frozen per session ([Hermes](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory)). ORFE chats run for a long time, so one freeze per chat is too long. Store the index text on the chat, and refresh it only at a cold moment. New notes stay reachable through `notes_search` until then.

## Code rules keep the vault tidy with little help from you

**Cheap checks at write time have the best support, and background tidying has the thinnest.** The field has settled on one shape: a small index, Markdown files read on demand, and version history. Anthropic's memory tool, Claude Code and Letta all ship it ([Anthropic](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool), [Claude Code](https://code.claude.com/docs/en/memory), [Letta](https://docs.letta.com/letta-code/memfs)). Karpathy reports that an index with no embeddings works at about 100 sources and hundreds of pages ([gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)). Almost nobody has published a controlled result showing that this improves outcomes.

The worst numbers come from a path you already rejected. One audit of automatic extraction found 97.8% junk across 10,134 entries. Most of it restated the system prompt or was noise ([Mem0 issue](https://github.com/mem0ai/mem0/issues/4573)). A model that chooses to save should avoid most of that. This is a reasoned guess, because no audit of tool-driven memory exists. One lesson does transfer. A hallucinated "User prefers Vim" grew to 808 entries because recalled memory was extracted again as new fact, and the pipeline had no way to reject a fact. A model that reads a note and saves its own paraphrase repeats this loop, only more slowly.

**Use a file surface over Dexie rows.** The model sees paths and Markdown. The app gets indexes. A few hundred notes do not justify a graph. Zep's graph needs model calls at ingest, and published benchmark scores are too disputed to choose by. One self-published audit of LoCoMo found 6.4% of its answer key wrong ([Penfield Labs](https://dev.to/penfieldlabs/we-audited-locomo-64-of-the-answer-key-is-wrong-and-the-judge-accepts-up-to-63-of-intentionally-33lg)). Each note needs a small required header: description, updated date, writer model. The notes used two tool name sets, and I chose this one.

| Tool | Job | Guard |
|---|---|---|
| `notes_search` | Find notes. Returns path, snippet, version | Capped results |
| `notes_read` | Read numbered lines. No path lists the tree | Character cap with paging |
| `notes_write` | Create, or replace a short note | Near-match check. Replace needs `expected_version`. Shrink guard |
| `notes_edit` | Replace exact text, or insert | Unique exact match. `expected_version` |
| `notes_delete` | Soft delete, or move with `new_path` | Goes to trash |

**Exact-match edits fail loudly, which is what you want.** Patch formats failed 50.7% of the time on Grok 4 and 46.2% on GLM-4.7. Hashline got worse on DeepSeek V3.2 ([Boluk](https://stencil.so/blog/the-harness-problem)). Hashline was also worse on Python in a second test, where the gap between models exceeded the gap between formats, and most failures were hallucinated `old_string` text ([nwyin](https://dev.to/nwyin/hashline-vs-replace-does-the-edit-format-matter-15n2)). All of this tests code, not prose, and both samples are small. Safety comes mainly from the host: version checks, a revision row in the same transaction, and no fuzzy matching.

**Sprawl control is a stack of plain rules.** Hard caps on the index and on working notes come first. Claude Code and Hermes both return an error that tells the model to fix the problem ([Claude Code](https://code.claude.com/docs/en/memory), [Hermes](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory)). This is your agent-driven tidy. The model does the work at the moment of overflow, with no schedule behind it. One vendor warns that squeezing under pressure can lose detail ([Vectorize](https://vectorize.io/articles/hermes-agent-memory-not-working)), and that claim is unproven. Second, `notes_write` returns near matches, so the model must choose update or create. Third, the instructions state a clear "nothing to save" path. The criteria that recur are durable, useful, stated or confirmed by you, and not found elsewhere ([OpenAI cookbook](https://developers.openai.com/cookbook/examples/agents_sdk/context_personalization)). Fourth, a deterministic lint finds orphans, broken links, oversize notes and near-identical titles. It needs no model and cannot damage anything.

**One audit shows gates help, but only roughly.** After four changes at once, junk fell from 97.8% to 46.6%. That sample was 73 entries over 48 hours, so no single change earns the credit ([Mem0 issue](https://github.com/mem0ai/mem0/issues/4573)).

**Drift is the larger risk, and labels do not fix it.** Across 16 models, agents checked a memory's source in about one episode in five. After a constraint was withdrawn, 74.7% to 77.3% of decisions still followed it. A content-free freshness cue did not help. One sentence telling agents to prefer memories that state a limit recovered 89.3 points on the decisions it targets ([Nakayashiki](https://arxiv.org/abs/2608.25553)). This is a single-author preprint in a controlled setup. It still argues for a concrete rule in the instructions and against a "may be stale" badge. Use `supersedes` links with a date, and keep the old note. Zep's four timestamps are too much for this scale.

**Tone and format drift between models is untested.** I found nothing on several models writing to one store. Your best tools are a writer stamp on every revision and one protected note of vault rules, like the schema file in Karpathy's pattern. A small eval per model comes next, because tool behaviour varies by model ([Anthropic](https://www.anthropic.com/engineering/writing-tools-for-agents)).

**Tidying should be a model session, split by risk.** Anthropic's dreams never change the input store, and you review the output ([Anthropic](https://platform.claude.com/docs/managed-agents/dreams)). Letta's defrag backs up first ([Letta](https://www.letta.com/blog/context-repositories)). Neither reports measured quality. One study comes close: giving a curator read-only tools to check memories raised pass rate from 39% to 73%, though checking was not isolated ([Suresh et al.](https://arxiv.org/abs/2609.11060)). ORFE has no backend, so "background" can only mean a run while the app is open. To keep your effort low, I suggest two tiers. Moves, tags and index edits apply at once with undo, because they cannot lose text. Merges and deletes wait as one diff with one tap. This split is my idea and has no direct evidence. Use a strong model for it, since the spread between models on story errors exceeded 30 times ([Lost in Stories](https://arxiv.org/html/2603.05890v1)). Skip automatic decay, because it could quietly bury a recipe you rarely open.

**The open thread on rerolls now has an answer.** Link every write to its message, and store the note's prior state, from day one. Memory Books added rollback only in August 2026, marked it breaking, and was still fixing it on 1 November ([changelog](https://raw.githubusercontent.com/aikohanasaki/SillyTavern-MemoryBooks/main/changelog.md)). Then undo a rerolled reply's chat-shelf writes, and keep its shared-shelf writes. Your proposal that new notes start on the chat shelf makes this clean. Moving a note to the shared shelf becomes the deliberate step. This policy is my inference.

## Only a lock in the tool code protects the poems

**No tool I found has a clean lock for curated text, so ORFE must enforce one itself.** Claude Code's docs say memory is "context, not enforced configuration" ([Claude Code](https://code.claude.com/docs/en/memory)). Three plain patterns do the protecting elsewhere. Keep the text in a separate container, make rewrites a preview, and keep the original. Memory Books is the best example. Its compaction shows the original next to the draft and "should never silently replace the original" ([Memory Books](https://raw.githubusercontent.com/aikohanasaki/SillyTavern-MemoryBooks/main/USER_GUIDE.md)). I found no evidence specific to poems or recipes. The nearest warning is measured: summaries raised plot holes about 50% for the best model ([Finding Flawed Fictions](https://arxiv.org/html/2504.11900v1)). Sudowrite's compression of 2,000 words of style into 40 shows the risk in product form ([changelog](https://feedback.sudowrite.com/changelog/22411)).

**Make protection one flag, not a second note type.** You chose one kind of note, and a flag keeps that. A `protected` note makes the tool handler refuse `notes_edit`, whole-note replace and delete. Move and tag still work. The refusal should give the next step: "This note is protected. Move or tag it, or write a new note that links to it." I suggest a one-way latch. Any model may turn the flag on, and only you can turn it off in the UI. The worst abuse is then a junk note you must unlock once.

**Tidying should never receive a protected body.** Send it only path, description and tags. Store a hash of each protected body, and compare it after every tidy. That gives mechanical proof that nothing changed. No tool I found does this, so treat it as my design, not a proven method.

**Avoid locked blocks inside editable notes.** Nobody has solved this visibly. Keep the block as its own protected note, and let the editable note link to it. The model edits around the link, and the block stays whole.

**Voice samples need a separate plan, because storage alone will not hold a voice.** A study of 400+ authors found five samples passed authorship checks 95 to 97% of the time on news and email, but only 19.37% on blogs. Adding more samples past a few changed little ([Catch Me If You Can?](https://arxiv.org/html/2509.14543v1)). So three to five short samples per voice is a fair start, at roughly 400 to 650 tokens by the notes' estimate. Informal voice is the hard case, and fiction may sit closer to blogs. That mapping is a guess. No study tests samples against descriptions for fictional characters. A pull-only method is to have the model read the voice note at chat start and again after each trim. Whether that is enough is exactly the open conflict in the first table.

## Compact at ORFE's trim, and search the real messages

**Production systems agree on the order.** They clear old tool results by rule, summarise the older middle, and keep the recent tail word for word. Manus, Hermes and LangChain's Deep Agents also keep an archive the model can search ([Manus via ZenML](https://www.zenml.io/llmops-database/context-engineering-for-production-ai-agents-at-scale), [Hermes](https://hermes-agent.nousresearch.com/docs/developer-guide/context-compression-and-caching), [LangChain](https://www.langchain.com/blog/context-engineering-deep-agents-remember)). ORFE gets the archive free, because every message stays on the phone.

**ORFE must write its own summariser.** Anthropic's summary block carries a signature, and OpenAI's is encrypted, so neither moves between models ([Anthropic](https://platform.claude.com/docs/en/build-with-claude/compaction-on-demand), [OpenAI](https://developers.openai.com/api/docs/guides/compaction.md)). OpenRouter's plugin only removes text from the middle ([OpenRouter](https://openrouter.ai/docs/transforms)).

**Trim events are the right trigger.** `planWindow` trims only on a hard limit or on a cold cache over the soft limit. The prefix is already broken at that moment, so a new summary adds no cache damage. Batch all prefix changes into that one event: trim, summary, tool result pointers and index refresh. Prepare the summary in the background so a send never waits. If it is late, trim anyway and fill it in next time, because the messages are safe. One code change follows. `messageChars` counts only message text, so `planWindow` must also count the summary block, the index and tool steps. Otherwise it will underestimate the window.

**Summarise fixed chunks and never rewrite the whole.** Factory's incremental method scored 3.70 against Anthropic's 3.44 and OpenAI's 3.35. All three fell to about 2.2 to 2.5 on specifics ([Factory](https://factory.com/news/evaluating-compression)). That test is vendor-run, on coding only, with a small margin, so "proven" is too strong. Recursive merging can amplify invented detail, and feeding the source back in helps ([Ou & Lapata](https://arxiv.org/html/2502.00977v2)). So tie each chunk to its source range and a hash, and build chapter roll-ups from originals when you can. OpenRouter's recipe uses chunks of about 16,000 characters, because one long call loses facts ([OpenRouter](https://openrouter.ai/docs/cookbook/building-agents/compact-agent-sessions-with-scaledown)). An edit inside a chunk changes the hash. The chunk is then marked stale and redone at the next cold moment. Rerolls stay in the verbatim tail and touch nothing.

**A story needs a story template.** Default prompts ask for state and next steps. In FABLES, 38.6% of unfaithful claims concerned character or relationship state, and 31.5% concerned specific events. Chronology errors appeared in 33.3 to 61.5% of summaries. Half the bad claims needed indirect reasoning to refute, so a reader will not catch them ([FABLES](https://arxiv.org/html/2404.01261v2)). These are 2024 models. Use sections for characters and state, relationships, events in order, open threads, world facts, and exact phrases. Ask only for what is on the page.

**Keep your own recent actions verbatim.** Adding hierarchical memory cut commitment conflicts from 26% to 4%, but conflicts with player input rose from 13% to 38% ([NCP-Bench](https://arxiv.org/html/2608.08160)). Compression helped plans and hurt respect for what the user just did. Your pinned messages already do the other half, and you choose them, which avoids the complaint that the model decides what matters ([Qvink](https://github.com/qvink/SillyTavern-MessageSummarize)).

**Hermes's budget does not fit your window.** Its minimum is 2,000 tokens, and its maximum is 5% of the window, or 1,600 tokens at 32,000. So ORFE needs its own numbers. I suggest about 15% of each span, with the whole block capped near 15% of the window. These are starting guesses. No study measures voice or prose quality after compaction. This is the largest gap, and your blind A/B page can fill it: same chat, summary against full context, vote on the next reply.

**Search needs two tools: `history_search` and `history_read`.** Search the verbatim messages, not the summaries, and cover only active versions outside the window. Return the hit plus one neighbour on each side, with message ids. Cap the rounds per turn. Letta's main finding is that searching again with a new query matters more than the engine ([Letta](https://www.letta.com/blog/benchmarking-ai-agent-memory)). Its 74.0% was not a pure keyword result, though, because its tools included semantic file search, and a full-context baseline scored 72.9% ([Zep](https://www.getzep.com/blog/lies-damn-lies-statistics-is-mem0-really-sota-in-agent-memory/)).

**Start with a Dexie term index.** One note suggested MiniSearch, but its in-memory index does not fit 100,000 messages on a phone, and its own design document rules out very large indexes ([MiniSearch](https://github.com/lucaong/minisearch/blob/master/DESIGN_DOCUMENT.md)). A multiEntry term index stays inside `storage.ts` and writes in the same transaction as the message ([JMP](https://blog.jmp.chat/tag/borogove)). Ranking is the cost. Put it behind an interface, so contentless FTS5 can replace it if a phone test shows a problem. All phone numbers are estimates, because no public benchmark covers this case.

**Finnish needs care.** Keep `ä` and `ö`, because folding merges different words. Index the raw token plus Finnish and English stems. Snowball has a Finnish stemmer ([Snowball](https://snowballstem.org/demo.html)). It does not split compounds, as far as I know, so use prefix search and let the model try the second part. The tool description can also ask for several inflected forms. That is free, though weak models will do it worse.

**Add embeddings second.** "Grep beats vectors" is overstated. Cursor measured 12.5% higher answer accuracy with both together, though it sells this feature ([Cursor](https://cursor.com/blog/semsearch)). Fiction memory also leans on meaning: "the scene where she forgave him" may share few words with the text. Cost is no barrier, at $0.02 per million tokens listed for one model ([OpenRouter](https://openrouter.ai/openai/text-embedding-3-small/pricing)). Two questions remain. CORS on `/embeddings` is unknown, and old chats would leave the phone for an embedding provider. Skip on-device embeddings. The smallest suitable model I found is 118 MB, and backfill would take hours of foreground compute by my estimate.

## Retrieved text goes in a tool result and stays there

**This is the simplest rule in the report.** A tool result is append-only history, so it never breaks the cache on any provider. Anthropic confirms the cache stays valid when only tool results are added ([Anthropic](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). The cost is that the text stays in context until a trim, read at the cache rate each turn. For model-driven retrieval, no breakpoint work is needed at all.

**Do not place vanishing text under ORFE's automatic breakpoint.** Automatic mode puts the breakpoint on the last cacheable block ([Anthropic](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)). If retrieved text sits last and is removed next turn, every cache entry ends in text that no longer exists. Each turn then pays a full write and reads nothing. This is reasoning from the documented rules and has not been observed, so one test should confirm it. If you ever port Mneme-style recall, this is the only case that needs a below-the-breakpoint design. Store the recall text as a kept part of the turn first. Build the vanishing form only if kept text costs too much.

**Treat everything above the messages as frozen.** Anthropic, OpenAI, Qwen and Kimi document tools as part of the prefix. Gemini, DeepSeek, xAI and GLM do not say, so assume the same ([OpenAI](https://developers.openai.com/api/docs/guides/prompt-caching), [Alibaba](https://www.alibabacloud.com/help/en/model-studio/explicit-cache-guide), [Kimi](https://platform.kimi.ai/docs/guide/use-context-caching-feature-of-kimi-api)). Send one stored JSON string. Keep note counts, dates and titles out of tool descriptions. Keep `tool_choice` constant, since a change drops Anthropic's message cache. Freeze the window start for a whole tool turn.

Code needs one fix here. `fingerprint()` in `src/lib/context.ts` hashes only the messages, so `isCold` will read warm after a tool list change.

**The one-hour cache has a trap.** Stickiness ends after 10 idle minutes, and a one-hour entry lives at one provider ([OpenRouter](https://openrouter.ai/docs/guides/best-practices/prompt-caching)). After a long pause, OpenRouter may route elsewhere, and you pay a miss plus a 2x write. Pinning with `provider.order` fixes this, but it turns stickiness off and needs listed fallbacks. Whether `session_id` outlasts 10 minutes is not documented. Qwen also gets no cache today, because it needs block markers and ORFE sends a top-level one only to Anthropic models.

**Mixed models need a rendering step.** Make the outgoing history a pure function of stored history and current model. Steps by the current model go out as real tool messages. Steps by other models are flattened into one assistant message, in plain past tense, such as "(Looked in notes for 'river': found 2 notes.)". Flattening avoids every ID trap in one move, and those are real: IDs over 1,000 characters bricked a session, and truncated IDs collided ([opencode #54146](https://github.com/anomalyco/opencode/issues/54146), [opencode #58323](https://github.com/anomalyco/opencode/issues/58323)). Models without tools get everything flattened and no `tools` field. Models with tools keep `tools` in every request while history holds tool messages ([OpenRouter](https://openrouter.ai/docs/guides/features/tool-calling)). After Stop, write a result for every call ID, or the next request fails ([Anthropic](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)). Whether JSON-shaped text makes models imitate calls is unmeasured, so plain text is the cautious choice.

**`reasoning_details` is the sharpest mixed-model risk.** Inside a tool loop, send it back unchanged, always. After a model switch, strip it at send time and keep it stored. Anthropic allows dropping it, and Gemini validates only the current turn. DeepSeek is the hard case. With `tools` present, it requires `reasoning_content` on all later requests, or it returns 400 ([DeepSeek](https://api-docs.deepseek.com/guides/thinking_mode)). Which OpenRouter field satisfies this is unclear, and one open report says the documented alias fails ([ai-sdk-provider #501](https://github.com/OpenRouterTeam/ai-sdk-provider/issues/501)). You rate DeepSeek highly, so test this first. Also accumulate reasoning by `index` in `send.ts`, because merging across indexes gives a signature error ([ai-sdk-provider #582](https://github.com/OpenRouterTeam/ai-sdk-provider/issues/582)).

## Plain rules keep tool results, a small model summarises, and Jev stays out

**Keep recent results whole, and turn older ones into pointers.** Manus says compression must stay restorable, because an agent cannot predict which observation will matter later ([Manus](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)). Anthropic calls clearing tool results one of the safest forms of compaction ([Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)). Its self-reported results are +29% for context editing alone and +39% with the memory tool, on one internal test ([Anthropic](https://www.anthropic.com/news/context-management)). All this evidence comes from coding and research agents, and no test compares clear, summarise and pointer directly.

ORFE is in an unusually good position. A search result is a copy of messages already on the phone, and a note read is a copy of a stored note. A pointer therefore loses nothing. At each trim, keep the three most recent tool uses, matching Anthropic's default ([Anthropic](https://platform.claude.com/docs/en/build-with-claude/context-editing)). Replace older ones with message ids or a path, plus one line. The stored turn keeps the full text. Summarising a search result is usually wrong, because it is exact story text, the very thing summaries lose. Keep the small model for bulky web pages.

**Your small summariser idea is sound, with one change: use a mid-tier model, not the cheapest.** Cognition reports using a dedicated compression model, and says it is hard to get right ([Cognition](https://cognition.com/blog/dont-build-multi-agents)). Hermes and the roleplay extension Qvink let you set a separate model for summaries ([Hermes](https://hermes-agent.nousresearch.com/docs/developer-guide/context-compression-and-caching?full=true), [Qvink](https://github.com/qvink/SillyTavern-MessageSummarize)). Evidence on tiers is indirect. Flash lost only 2.3 points to Pro at a 3.7x cost difference, while Flash Lite did much worse, but that measures answering ([ConvoMem](https://arxiv.org/html/2511.10523v1)). Unfaithful claims ranged from 2.1% to 11.47% by model on old models ([FABLES](https://arxiv.org/html/2404.01261v2)). Nothing directly measures summariser tier for conversation compaction.

Cost will not decide this. The compaction note used stale prices, so I redid the sum with the feed prices from 1 November. Summarising a 9,600-token span costs $0.00096 of input on Haiku 5.5. A cold 32,000-token window on Sonnet 5.5 costs $0.064, and a warm one costs $0.0032 ([models feed](https://openrouter.ai/api/v1/models)). A small model wins even against a warm cache, on input alone. A cheap model also cannot read your main model's cache, so span-only input is the right design. The first models to compare are `scaledown/summarize`, `qwen/qwen3.7-flash`, `inception/mercury-2.5`, and Haiku 5.5 as the reference. Check that each one's `context_length` covers the span, because a smaller window is the most common cause of bad compaction in Hermes ([Hermes](https://hermes-agent.nousresearch.com/docs/developer-guide/context-compression-and-caching?full=true)). No source ranks these on Finnish, so a blind A/B fits. Avoid models with mandatory reasoning.

**Jev should not decide what is kept.** I found no production system that uses a per-result classifier. Every rule I found is plain: keep the last N, or act on size or age. That is absence of evidence only. The argument is stronger than the evidence, and it has three parts. When dropping is reversible, a wrong call costs almost nothing, so the classifier saves little. When dropping is not reversible, a cheap model is the wrong judge. And clearing a result breaks the cache ([Anthropic](https://platform.claude.com/docs/en/build-with-claude/preserved-thinking)), so a decision made per result must wait for the next trim anyway. The rule at the trim already does that job with no network call. No source gives a phone latency figure, but every extra round trip is felt on mobile.

The notes disagree here, so I must flag it. One note says skip Jev for retention. Another proposes Jev for "Does this turn need memory?" and "Is this note worth saving?". **The first of those conflicts with your rule.** A gate that decides when memory is relevant is automation by another name. Reject it. The second could flag a save, but it has no evidence behind it. Near-match checks should come first.

Jev's best fit is yes/no work where a wrong answer costs only a look. During tidying it could ask "Are these two notes the same thing?" to pick merge candidates for your diff. It is cheap: Mai's log puts 20 calls near $0.0005. It worked on Finnish there after examples (FI 10/12, `E:/Claude/Context/mai.log.md`). The endpoint allows browser calls by preflight, but the path says alpha ([Jev tutorial](https://openrouter.ai/docs/guides/community/jev-tutorial)). This use is my suggestion and is untested.

## Abilities work best as plain data behind one function

**Build a static TypeScript registry, not a plugin system.** The proven module shape is small: a short description always visible, instructions on demand, tools as JSON Schema, and a handler ([Agent Skills](https://agentskills.io/specification)). TypingMind, the closest browser app, uses nearly this shape ([TypingMind](https://docs.typingmind.com/plugins/build-a-typingmind-plugin)). The bloat is also documented. A five-server MCP setup used about 55K tokens before the chat began ([Anthropic](https://www.anthropic.com/engineering/advanced-tool-use)). MCP's own 2026 revision removed its stateful parts and kept tools ([MCP](https://modelcontextprotocol.io/specification/2026-07-28/changelog)). Open marketplaces fared worst: Snyk found security issues in 36.82% of 3,984 skills and 76 confirmed malicious payloads ([Snyk](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub)). The "proven" judgement is my reading of adoption and failures. No study measures module formats directly.

```ts
// Design sketch, not sourced
interface Ability {
  id: string; title: string; summary: string
  tools: ToolDef[]                          // data only, with fixed order
  run(call, ctx): Promise<ToolResult>       // ctx is narrow, never the Dexie handle
  hooks?: { beforeSend?(plan, ctx): plan }  // compaction lives here, not as a tool
  traits: { private?: true; untrusted?: true; outward?: true }
}
```

Compaction shows why an ability needs two kinds of parts. It changes the send plan, and no model calls it. One host function, `toolsFor(chat, model)`, decides what reaches the model. That gives you a seam: a dispatcher can replace direct tools later without changing any ability.

**Stay at or below about 12 tools per request.** Anthropic says selection degrades past 30 to 50 tools, and OpenAI suggests fewer than 20 ([Anthropic](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool), [OpenAI](https://developers.openai.com/api/docs/guides/function-calling)). GitHub cut Copilot from 40 tools to 13 and reports 2 to 5 points better success ([GitHub](https://github.blog/ai-and-ml/github-copilot/how-were-making-github-copilot-smarter-with-fewer-tools/)). A small thesis through OpenRouter shows models getting worse as tools grow, noisily, with confusable tools as the main harm ([Wiberg and Diana](https://liu.diva-portal.org/smash/get/diva2:2072520/FULLTEXT01.pdf)). Notes plus history is seven tools. `notes_search` and `history_search` are the risky pair, so their descriptions must say what each covers. The 12 is a judgement from these sources, not a measured limit.

**A toggle costs one cold turn, and that is fine.** The notes conflict here. One says never vary the tool list. The other accepts a change on toggle. Both hold if the list is frozen for a chat between your own toggles. With current prices, a cold turn costs 25x a warm one for the cached part on Opus and Sonnet 5.5, and 12.5x on Haiku 5.5. The notes' 12.5x used the older general rate. If the cache is already cold, a toggle costs nothing. Default sets attached to a prompt make toggles rare. Skip OpenRouter's tool search, since it needs unaltered history and ORFE rewrites history at each model switch ([OpenRouter](https://openrouter.ai/docs/guides/features/server-tools/tool-search)).

**Leave MCP for later.** A browser can be a client for remote Streamable HTTP servers that allow cross-origin calls, but nothing requires them to ([MCP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)). `stdio` is impossible, and WebMCP runs the other way. Keep the shape compatible, so one "remote MCP" ability can map remote tools later.

**Fix one leak before notes ship.** `src/lib/markdown.ts` allows `style`. In a sanitiser-level test, a `background-image:url(...)` span survived with data in the URL. It was not tested on a live page. That could become a zero-click leak of private notes, so move the property allowlist forward from Plan 5 and add a meta CSP. Then use the traits. If a chat holds private data, untrusted content and an outward channel at once, warn or refuse. This is the "lethal trifecta" rule, and removing one leg breaks the attack ([Airia](https://airia.com/blog/ai-security-in-2026-prompt-injection-the-lethal-trifecta-and-how-to-defend/)). Note writes after untrusted content should be held for a visible confirm, because poison in memory persists ([MemoryGraft](https://arxiv.org/html/2512.16962)). Show every write as a chip with undo. User-made modules, if they ever come, belong in a `srcdoc` iframe with `sandbox="allow-scripts"` only. A Web Worker alone is not a boundary.

## Conclusion

ORFE's constraints turn out to help it. Other systems must work to keep originals restorable. Your phone already keeps every message, so nearly every step can be reversed. The trim you already built is also more useful than it looks. It is the one moment when the prefix is already broken, so the summary, the pointers and the index refresh can all land there for free. And "agent-driven" gets a concrete meaning from this research. The model does the curating, and code sets the walls. A cap error makes the model tidy, a near-match makes it choose, and a refused edit keeps it off the poems. Mneme automates the decision. ORFE should automate only the limits.

The largest unknown is the one that makes ORFE unusual: nobody has studied several models writing to one store over months. So your data will soon be better than the literature on this point, if every revision carries its writer from the first day. I would build in this order: the `style` fix and CSP, backup, the vault with revisions and message-linked writes, the `reasoning_details` rendering tests alongside the tool loop, history search, compaction, and tidying last. Write the amended rule into the design doc before any of it.
